# GCP Resource Hierarchy

## The chain

```
Organization (1)
   |
   +-- Folder (0..many)          optional, for grouping departments/teams
         |
         +-- Project (1..many)   the actual unit of work
               |
               +-- Resources (1..many)   VMs, buckets, SQL instances, etc.

Billing Account (0..many, separate tree)
   |
   +-- linked to --> Project (many-to-one: many projects can share one billing account)
```

## What each thing actually is

- **Organization**: the root node tied to a Google Workspace / Cloud Identity domain
  (e.g. `ashfaq786786-wwe-org`). One org per company, normally. Everything else
  nests under it. A personal Gmail account (not Workspace) typically has *no*
  organization — projects just float at the top level, which is our current setup.
- **Folder**: optional grouping under an org, usually mirrors company structure
  (`Engineering`, `Finance`, `prod`, `nonprod`). Folders can nest inside folders.
  Not required for small setups or learning.
- **Project**: the real container for resources. Every VM, bucket, SQL instance,
  IAM policy, API enablement — all scoped to exactly **one** project. This is the
  unit you enable APIs on, set quotas on, and bind IAM roles on.
- **Billing account**: a *separate* hierarchy, not a child of org/folder/project.
  It represents a payment method + invoicing profile. A project has **at most one**
  linked billing account at a time, but one billing account can fund **many**
  projects (1 billing account : many projects). If a project has no billing
  account linked, most paid APIs refuse to enable.
- **Resources**: the actual things you create (Compute VM, Cloud SQL instance,
  GCS bucket, custom IAM role, service account...). Always scoped to one project.

## A project actually has three different "names"

| | Example | What it's for |
|---|---|---|
| **Project name** | `My First Project` | Human-friendly label, purely cosmetic. Can be renamed anytime, not required to be unique. Shown in the Console project switcher. |
| **Project ID** | `project-3d2fd1eb-6dd8-40b6-958` | The REAL identifier. Globally unique across all of GCP, forever, and cannot be changed once set. Appears in every API call, `gcloud` command, and resource name (service account emails, IAM role paths, etc) - this is what we use everywhere in this repo's code. |
| **Project number** | e.g. `884717715366` | A numeric ID GCP auto-assigns, used internally by some APIs/services. Rarely typed by hand (you may spot it in `gcloud services enable` output). |

Same project, three names. This one's ID was auto-generated by Google
because the project was auto-created at sign-up rather than deliberately
created by us - if you create a project yourself later, you choose the ID
(subject to uniqueness/format rules), and you'd typically pick something
readable like `gcp-learning-lab-prod` instead of a random one like this.

## Cardinality cheat sheet

| Relationship | Cardinality |
|---|---|
| Organization -> Folder | 1 : many |
| Folder -> Folder | 1 : many (nesting) |
| Folder/Org -> Project | 1 : many |
| Billing account -> Project | 1 : many |
| Project -> Billing account | many : 1 (a project has only one *active* linked billing account) |
| Project -> Resources (VMs, buckets, roles...) | 1 : many |
| Project -> Custom IAM roles | 1 : many (roles we create are project-scoped unless created at org level) |
| Service account -> IAM role bindings | many : many (a role can be bound to many identities, an identity can hold many roles) |

## Why this matters day to day

- **IAM roles bind at a resource level in this hierarchy** — a role granted at
  Org level cascades down to every Folder/Project/Resource under it; a role
  granted at Project level only applies inside that project. Real companies
  grant broad roles high up (e.g. "SecurityAdmin" at Org) and narrow roles low
  down (e.g. "backendDeveloper" at one Project) — this is exactly the pattern
  we're simulating.
- **Billing is intentionally decoupled from the org/project tree** so finance
  can manage payment methods without touching resource permissions, and so
  multiple unrelated projects can share one company credit card.

## The Console project selector controls where everything you create lands

Every resource created via the Console UI - service account, custom role,
bucket, VM, anything - is created inside whichever project is currently
selected in the project picker at the top of the page (next to the Google
Cloud logo). This is not a display filter, it is the actual scope of the
create call. If you ever work across multiple projects, check the selector
before creating something, the same way you'd check which `gcloud config`
project is active before running a CLI command (see `local-setup.md`).
